# Funnel Runtime

Мини-платформа для запуска, версионирования и анализа многошаговых веб-воронок.

Фронтенд не содержит ни одного захардкоженного экрана: воронка целиком — шаги, тексты, валидация,
условная видимость, правила выбора результата — приходит с бэкенда JSON-конфигом. Версии конфига
публикуются и откатываются без передеплоя, сессия навсегда закрепляется за версией, на которой началась,
а события пишутся в собственный идемпотентный endpoint и агрегируются по уникальным сессиям.

**Живой стенд: https://109-120-178-184.sslip.io** — [воронка](https://109-120-178-184.sslip.io),
[версии](https://109-120-178-184.sslip.io/admin/versions),
[дашборд](https://109-120-178-184.sslip.io/admin/analytics).
**Репозиторий: https://github.com/doloradium/fintech-test**. Админ-токен стенда передаётся вместе
со ссылками (в письме).

Всё содержимое воронок вымышленное. Внешних сервисов нет: хранилище — SQLite внутри проекта.

## Быстрый старт

Требуется **Node.js 24+** (используется встроенный модуль `node:sqlite`, нативных зависимостей нет).

```bash
npm install
npm run dev
```

- воронка — http://localhost:5173
- управление версиями — http://localhost:5173/admin/versions
- дашборд — http://localhost:5173/admin/analytics

Vite проксирует `/api` на бэкенд (http://localhost:3000). При первом запуске сервер публикует
`configs/funnel-v1.json` как активную версию и создаёт `data/funnel.sqlite`.

Наполнить базу синтетическим трафиком (сервер должен быть запущен):

```bash
npm run seed
```

Сборка и запуск одним процессом (API отдаёт и статику фронтенда):

```bash
npm run build
npm start
```

Полезное:

```bash
npm test          # автотесты
npm run typecheck # tsc по всем пакетам
npm run reset     # удалить базу и начать с чистого листа
```

Переменные окружения — в [.env.example](.env.example). Если задать `ADMIN_TOKEN`, внутренние страницы
начнут требовать заголовок `x-admin-token` (поле для токена есть в самой админке).

## Что где лежит

```
packages/shared/            Общий код фронта и бэка
  src/funnel-config.ts        zod-схема конфига и проверка целостности
  src/conditions.ts           язык условий и его интерпретатор
  src/resolve.ts              сборка варианта, видимость шагов, прогресс, выбор результата, валидация
  src/events.ts               схема входящего события
  src/api-types.ts            контракты ответов API
apps/api/                   Fastify + SQLite
  src/db/                     подключение и миграции
  src/domain/                 версии, сессии, приём событий, аналитика, назначение варианта
  src/routes/                 публичные и админские ручки
  src/scripts/                генератор трафика
  tests/                      vitest
apps/web/                   React + Vite + Tailwind + shadcn/ui
  src/funnel/                 рантайм воронки
  src/admin/                  версии и дашборд
  src/components/ui/          компоненты shadcn/ui (вендорятся в репозиторий, не зависимость)
  src/lib/tracker.ts          очередь событий с батчингом и ретраями
  src/lib/theme.tsx           светлая и тёмная тема без мигания при загрузке
deploy/                     systemd-юнит, конфиг nginx, скрипт деплоя
```

Атрибут `lang` на странице воронки берётся из `locale` конфига (у присланной воронки — `en-AU`),
чтобы скринридеры читали английский контент английской фонетикой; админка остаётся `ru`.

UI собран на **shadcn/ui** поверх Tailwind v4 и Radix: компоненты лежат прямо в репозитории
(`src/components/ui`), а не приходят пакетом, поэтому их можно править под задачу. Тема светлая
и тёмная, переключается в шапке и запоминается; класс проставляется инлайновым скриптом до первой
отрисовки, чтобы не мигало. Сборка разложена на чанки: react, router, ui и код приложения — около
171 KB gzip суммарно.

Ключевое решение: `packages/shared` — единственный источник правды о структуре воронки. Бэкенд и
фронтенд считают видимость шагов, прогресс, выбор результата и валидность ответа **одним и тем же
кодом**, поэтому клиент не может разойтись с сервером в понимании ветвлений.

## Конфиг воронки

Формат — тот, что пришёл вместе с заданием. Один конфиг описывает воронку целиком: пул шагов,
два варианта эксперимента поверх него, правила выбора результата и каталог событий.

```jsonc
{
  "schemaVersion": "1.0",
  "funnelId": "workstyle-planner",
  "locale": "en-AU",
  "title": "Find your team's operating style",
  "session":  { "ttlHours": 72, "persistAnswers": true, "pinVersion": true, "pinExperimentVariant": true },
  "progress": { "countVisibleOnly": true, "excludeTypes": ["info", "result"] },
  "experiment": {
    "id": "question-order-and-result-framing-v1",
    "assignment": "server",
    "sticky": true,
    "overrideQueryParam": "variant",
    "variants": {
      "A": { "weight": 50, "stepSequence": ["intro", "…", "result"], "stepOverrides": {}, "resultOverrides": {} },
      "B": { "weight": 50, "stepSequence": ["…"], "stepOverrides": { "intro": { "content": { "title": "…" } } },
             "resultOverrides": { "async_native": { "title": "…", "cta": { "label": "…" } } } }
    }
  },
  "steps": { "…": { "id": "…", "type": "…", "content": {}, "input": {}, "validation": {}, "visibleWhen": {} } },
  "resultRules": [{ "resultId": "async_native", "when": { "any": [ … ] } }],
  "defaultResultId": "balanced",
  "results": { "async_native": { "title": "…", "summary": "…", "recommendations": [], "cta": {} } },
  "events": { "baseProperties": [], "allowed": [], "privacy": { "storeRawAnswers": false } }
}
```

**Типы шагов:** `info`, `number`, `single-select`, `multi-select`, `result`.

**Ветвление** задаётся через `visibleWhen` на самом шаге, а не через переходы. Шаг с невыполненным
условием просто выпадает из пути, и следующий шаг подтягивается на его место:

```json
"visibleWhen": { "answer": "work_mode", "operator": "in", "value": ["hybrid", "office"] }
```

Поддерживаемые операторы: `eq`, `neq`, `in`, `notIn`, `contains`, `containsAny`, `containsAll`,
`gt`, `gte`, `lt`, `lte`, `between`, `isAnswered`, `isEmpty`. Композиты: `all`, `any`, `none`, `not`.
Конфиг из задания использует подмножество (`eq`, `in`, `any`, `all`) — остальное добавлено, чтобы
следующая итерация не упёрлась в язык условий.

**Экран результата не один.** Шаг типа `result` не содержит текста: он берёт `resultSource: "resultRules"`,
правила проверяются по порядку, первое сработавшее даёт `resultId`, иначе берётся `defaultResultId`.
Все четыре результата описаны в `results`, вариант B переопределяет их заголовки и CTA через
`resultOverrides`. Выбранный результат сохраняется в сессии и попадает в аналитику.

**CTA делает то, что объявлено в конфиге.** У каждого результата есть `cta.action`, и в присланном
конфиге это `expand_recommendation`. Поэтому список `recommendations` спрятан за кнопкой: экран
результата показывает заголовок, резюме и сводку ответов, а клик по CTA раскрывает рекомендации и
отправляет `cta_clicked` со свойствами `result_id` и `action` — ровно теми, что перечислены у этого
события в `events.allowed`. Если бы рекомендации показывались сразу, кнопка была бы пустышкой,
а `cta_ctr` — основная метрика эксперимента — считался бы по клику в никуда.

**Прогресс** считается по `progress`: только доступные пользователю шаги (`countVisibleOnly`) и без
служебных типов (`excludeTypes: ["info", "result"]`).

Тонкость: наивная реализация здесь дёргается. Если считать в знаменателе только те шаги, что видимы
прямо сейчас, то `office_days` не попадает в него, пока не отвечен `work_mode`, — и в середине воронки
знаменатель прыгает с 6 на 7, а кнопка «Назад» откатывает полосу сильнее, чем на один шаг.

Поэтому знаменатель считается **по состоянию на момент прихода на шаг**: учитываются ответы только
на шаги, идущие раньше текущего, а условная ветка попадает в знаменатель, пока ответ окончательно
её не исключил. Даёт три полезных свойства:

- полоса растёт монотонно, пока пользователь идёт вперёд;
- возврат на шаг показывает ровно то же значение, что и первый визит на него;
- знаменатель меняется максимум один раз — когда ветка отпадает, и прогресс при этом прыгает вперёд,
  а не назад.

Служебные экраны не участвуют в нумерации: в ответе сессии есть `progress.counted`, и фронтенд
показывает «Введение» вместо «Шаг 1 из 7» на вводном экране. Всё это покрыто тестами в
`publish-rollback.test.ts`.

Две отдельные засады уже на стороне фронтенда, обе дают дёргающуюся полосу.

Первая — вёрстка. У индикатора `Progress` из shadcn стоит `transition-all`, а сдвиг задан в процентах
от собственной ширины. Экраны разной высоты, поэтому между шагами появляется и пропадает вертикальный
скроллбар, контейнер меняет ширину — и полоса анимирует ширину одновременно с трансформом. Лечится
`transition-transform` вместо `transition-all` и `scrollbar-gutter: stable` на `html`. Заметно только
там, где скроллбар занимает место: на macOS с оверлейными полосами прокрутки этого не видно.

Вторая — порядок обновлений в React, и она куда коварнее. `react-router` оборачивает смену URL в
`startTransition`, а обычный `setState` — срочное обновление. React коммитит их **разными рендерами**:
сначала новый шаг со старым URL, и только потом URL догоняет. Эффект, который синхронизирует шаг с
адресной строкой, в этот промежуток видит рассинхрон, принимает его за нажатие «Назад», откатывает
сессию на предыдущий шаг и шлёт ложное событие `back_clicked` — а следом всё возвращается обратно.
Полоса успевает съездить вперёд, назад и снова вперёд, а аналитика получает возврат назад на каждом
шаге вперёд.

Поэтому источник правды о текущем шаге — **адресная строка**. Ответ на шаг не вызывает `setState`
напрямую: свежая сессия кладётся в ref, вызывается `navigate`, и уже эффект, увидев нужный `?step=`
в URL, достаёт её из ref без похода на сервер. Порядок коммитов перестаёт что-либо значить.
Проверено в браузере наблюдателем за атрибутом `style` полосы: на каждый шаг ровно одна запись,
значения монотонны, а `back_clicked` появляется только при реальном возврате.

**Вариант** задаётся тремя вещами: `stepSequence` (какие экраны есть и в каком порядке),
`stepOverrides` (патч шага — `content` сливается по ключам, `input` и `validation` тоже) и
`resultOverrides` (патч конкретного результата). Чтобы убрать экран у варианта, достаточно не
упоминать его в `stepSequence`.

**Валидация** живёт в конфиге: `validation.required`, `minSelections`, `maxSelections` и словарь
`messages`. Сообщение из конфига показывается пользователю дословно; в коде остались только запасные
формулировки на случай, если конфиг сообщение не задал.

Форма шага помечена `noValidate` — иначе нативная валидация браузера перехватывает отправку раньше
нашего кода и показывает свою подсказку на языке браузера («Значение должно быть меньше или равно 5»
на англоязычной воронке), а `messages.max` из конфига не показывается никогда. Атрибуты `min`/`max`
на поле оставлены ради стрелок и мобильной клавиатуры. Кратность числового ответа проверяется для
любого `input.step`, включая дробный: значение должно отстоять от `min` на целое число шагов.

**Целостность конфига** проверяется zod-схемой при публикации: id шага совпадает с ключом, `stepSequence`
ссылается на существующие шаги и не содержит дублей, у каждого варианта минимум 6 экранов и он
заканчивается шагом `result`, `resultRules` и `defaultResultId` ссылаются на существующие результаты,
все семь обязательных событий объявлены. Невалидный конфиг не публикуется — 400 с перечнем проблем.

Визуальный редактор конфигов не делался (по ТЗ не требуется): публикация идёт файлом из репозитория
или вставкой JSON в поле админки.

### Что лежит в `configs/`

| Файл | Что это |
| --- | --- |
| `funnel-v1.json` | Конфиг, пришедший вместе с заданием. 9 экранов, ветвление по `work_mode`, 4 результата |
| `funnel-v2.json` | Написан мной как вторая итерация, пока не пришёл настоящий конфиг: новая условная ветка `meeting_load`, у варианта B удалён экран `tool_count`, добавлено событие `recommendation_expanded`, добавлено правило результата |
| `funnel-minimal.json` | Служебный: минимум, проходящий валидацию (6 экранов, два варианта, два результата). Удобен, чтобы проверить публикацию и откат, не трогая основные воронки |

Имя файла не равно номеру версии: номер выдаёт база при публикации, поэтому один и тот же файл можно
опубликовать повторно и получить новую версию.

## Версионирование и откат

- `funnel_versions` хранит все опубликованные конфиги, `funnel_state.active_version` — текущий активный.
- **Публикация** не требует передеплоя: конфиг попадает в базу и активируется одним запросом.
- **Сессия закрепляется за версией** в момент создания (`sessions.funnel_version`) и больше её не меняет.
  Публикация новой версии не влияет ни на одну живую сессию: она дочитает свои экраны на старом конфиге.
- **Новые сессии** стартуют только на активной версии.
- **Откат** — активация более раннего номера. Отдельной сущности «rollback» нет: событие пишется
  в журнал `version_activations` с действием `rollback`, если новый номер меньше текущего.
- Аналитика при откате не теряется: события хранят номер версии, дашборд сравнивает версии.

Схема базы при этом не меняется. Новое событие второй итерации (`recommendation_expanded`) не требует
миграции: `events.name` — обычная строка, а список допустимых имён и их свойств берётся из конфига той
версии, к которой привязана сессия. Событие, не объявленное в её версии, отклоняется как
`unknown_event_name` — это защита от мусора, а не ограничение схемы.

## A/B-эксперимент: гипотеза и метрика

Эксперимент задан конфигом: `question-order-and-result-framing-v1`, назначение на сервере, липкое
в рамках сессии, override через query-параметр `variant`.

**Гипотеза.** Вариант A начинает с вопроса о размере команды — абстрактного и не связанного с болью
пользователя. Вариант B меняет две вещи сразу: спрашивает сначала о режиме работы и разбросе часовых
поясов (то, ради чего человек и пришёл), а на экране результата заменяет описательные заголовки
на обещание действия («Your team is ready to reduce meetings» вместо «Async-native») и CTA
«See the 30-day action list» вместо «View the action list». Ожидание: релевантный первый вопрос
снижает отвал на старте, а конкретный CTA повышает долю кликов среди дошедших.

**Основная метрика:** `cta_ctr` — доля уникальных сессий, в которых был `cta_clicked`, от всех сессий
варианта. Дашборд показывает её и uplift B к A. Клик по CTA — реальное действие: он раскрывает список
рекомендаций, спрятанный за кнопкой, поэтому метрика измеряет интерес к плану действий, а не случайное
нажатие.

**Вспомогательные метрики:** конверсия в результат (`result_viewed` / сессии) и пошаговый отвал —
чтобы отличить «CTR вырос, потому что дошло больше людей» от «CTR вырос при том же трафике».
Плюс разрез по экранам результата: вариант B переписывает их тексты, и полезно видеть, на каком из
четырёх результатов эффект есть, а на каком нет.

**Про смешение факторов — честно.** Вариант B меняет две вещи сразу: порядок вопросов и подачу
экрана результата. По одной только основной метрике нельзя сказать, какое из изменений сработало, —
это осознанное свойство присланного конфига, а не наш выбор: id эксперимента буквально называется
`question-order-**and**-result-framing-v1`, то есть проверяется связка изменений целиком. Такой
«бандл-тест» — нормальная практика для первой итерации: сначала выясняют, работает ли направление
вообще, и лишь потом раскладывают на факторы.

Частично разложить эффект дашборд всё же позволяет. Конверсия в результат реагирует только на
порядок вопросов — оформление результата пользователь к этому моменту ещё не видел. А строка
`result` в таблице шагов показывает CTR среди дошедших — на него влияет в основном подача CTA.
Разложение не строгое: до результата в варианте B доживает другая популяция, чем в A (ошибка
выжившего), поэтому для чистой атрибуции понадобился бы факторный дизайн 2×2 — четыре варианта
вместо двух. Формат конфига это уже позволяет: вариантов может быть сколько угодно, и аналитика
считает uplift каждого к контролю.

**Назначение варианта** делает бэкенд в момент создания сессии: `sha256(salt + experiment_id + session_id)`
раскладывается по весам вариантов, результат сразу пишется в `sessions.variant`. Поэтому вариант
стабилен по построению — он не пересчитывается ни при refresh, ни при переоткрытии страницы.
Сессия с override помечается `variant_source = "override"`, и её видно в данных.

Имя query-параметра для override сервер берёт из конфига (`experiment.overrideQueryParam`), а не
хардкодит. Ключи вариантов — тоже: нигде в коде нет захардкоженных «A» и «B», рантайм работает
с любыми именами (`control`/`turbo` и сколько угодно вариантов — это покрыто тестом), а генератор,
фильтр аналитики, кнопки в админке и расчёт uplift берут ключи из конфига или из данных. Значение
override распознаётся без учёта регистра: `?variant=b` сработает как `B`, а мусор вроде
`?variant=zzz` просто игнорируется — сессия создаётся с обычным серверным назначением, а не падает
с ошибкой.

Override работает и при живой сессии: если открыть ссылку с валидным вариантом, отличным от
варианта текущей сессии, клиент начинает новую сессию с запрошенным вариантом — иначе параметр
«для проверки» молча игнорировался бы у всех, кто уже начал воронку. Тот же параметр с тем же
вариантом (обычный refresh) сессию не трогает, мусорное значение — тоже.

Резолв варианта выполняется **на сервере**: клиент получает уже собранный конфиг своего варианта
и физически не видит альтернативный.

## Модель данных

SQLite, миграции применяются при старте (`schema_migrations` + список в `apps/api/src/db/migrations.ts`).

| Таблица | Назначение |
| --- | --- |
| `funnel_versions` | `version` (PK), `funnel_id`, `title`, `schema_version`, `config_json`, `checksum`, `source`, `notes`, `created_at` |
| `funnel_state` | Одна строка: `active_version` |
| `version_activations` | Журнал: `version`, `action` (`publish` / `activate` / `rollback`), `actor`, `note`, `created_at` |
| `sessions` | `id` (uuid), `funnel_id`, `funnel_version`, `experiment_id`, `variant`, `variant_source`, `current_step_id`, `result_id`, пять `utm_*`, `created_at`, `last_seen_at`, `expires_at`, `completed_at` |
| `session_answers` | `(session_id, step_id)` → `value_json`. **Сырые ответы живут только здесь** |
| `events` | `event_id` (PK), `session_id`, `name`, `funnel_id`, `funnel_version`, `experiment_id`, `variant`, `step_id`, `result_id`, `seq`, `client_timestamp`, `server_timestamp`, пять `utm_*`, `properties_json` |
| `ingest_stats` | Счётчики принятых / отброшенных как дубли / отклонённых событий |

Разделение `session_answers` и `events` — сознательное: ответы пользователя нужны рантайму воронки
(чтобы посчитать видимость шагов, выбрать результат и показать сводку), но в аналитику они не попадают.
Это ровно то, что конфиг требует через `events.privacy.storeRawAnswers: false`.

`sessions.expires_at` считается из `session.ttlHours` конфига. Обращение к истёкшей сессии отдаёт 410,
и клиент начинает новую — вместо того чтобы молча показывать пустую воронку.

События при этом принимаются и для истёкших сессий — сознательно. Клиентская очередь хранится в
`localStorage` и досылается при следующем открытии страницы: если человек вернулся позже TTL, его
события описывают действия, которые реально произошли до истечения, и терять их из аналитики
неправильно. Идемпотентность от этого не страдает — `event_id` остаётся первичным ключом.

## Event schema

Тело запроса — либо одно событие, либо пачка `{ "events": [...] }`.

Клиент присылает:

| Поле | Тип | Обязательно |
| --- | --- | --- |
| `event_id` | string, 8..64 символа, уникальный | да |
| `session_id` | string | да |
| `name` | snake_case, из `events.allowed` конфига | да |
| `client_timestamp` | ISO 8601 со смещением | да |
| `seq` | int, порядковый номер внутри сессии | нет |
| `step_id` | string | для шаговых событий — да |
| `properties` | объект скаляров | нет |

Сервер добавляет `server_timestamp` и **выводит из сессии** `funnel_id`, `funnel_version`,
`experiment_id`, `variant` и `utm_*` — то есть весь `baseProperties` из конфига. Эти поля не берутся
с клиента: иначе версию и вариант можно было бы подменить и испортить аналитику.

**Каталог событий берётся из конфига**, а не зашит в код. Имя события должно быть объявлено в
`events.allowed` той версии, к которой привязана сессия, а из `properties` сохраняются **только те
ключи, что перечислены у этого события**:

| Событие | Свойства из конфига |
| --- | --- |
| `session_started` | — |
| `step_viewed` | `step_type`, `visible_step_index`, `visible_step_count` |
| `answer_submitted` | `answer_kind` |
| `step_completed` | `next_step_id` |
| `back_clicked` | `destination_step_id` |
| `result_viewed` | `result_id` |
| `cta_clicked` | `result_id`, `action` |

Поэтому «сырые ответы не попадают в аналитику» — не эвристика, а следствие контракта: у
`answer_submitted` объявлен единственный ключ `answer_kind`, и всё остальное отбрасывается на входе.
Флаг `privacy.allowAnswerKinds` отключает и его.

### Инварианты приёма

| Требование | Как обеспечено |
| --- | --- |
| Повторный `event_id` не создаёт дубль | `event_id` — первичный ключ, вставка через `INSERT OR IGNORE`; дубли внутри пачки схлопываются до вставки |
| Пачки | `POST /api/events` принимает до 500 событий за раз, вставка в одной транзакции |
| Повторный запрос после timeout безопасен | Приём идемпотентен: повторная отправка той же пачки даёт `accepted: 0, duplicates: N` |
| Одно плохое событие не ломает пачку | Каждое событие валидируется отдельно; плохие возвращаются в `rejected` с причиной, остальные принимаются |
| Сырые ответы не утекают | Allowlist свойств из конфига, см. выше |

Ответ:

```json
{ "received": 6, "accepted": 4, "duplicates": 1,
  "rejected": [{ "index": 2, "event_id": "…", "reason": "unknown_session" }] }
```

Причины отклонения: `validation_failed`, `unknown_session`, `unknown_event_name`, `missing_step_id`, `unknown_step`.

### Клиентская доставка

`apps/web/src/lib/tracker.ts` держит очередь в памяти и в `localStorage`, отправляет пачками
(по 25 событий или раз в 2 секунды), при неудаче оставляет пачку в очереди и повторяет позже,
а на `pagehide` досылает хвост через `sendBeacon`. Поскольку `event_id` генерируется в момент
постановки в очередь, любые повторы схлопываются на сервере.

## Правила агрегации

Главный принцип: **все показатели считаются по уникальным сессиям, а не по количеству событий.**

Из базы забираются `DISTINCT (session_id, name, step_id)` по отфильтрованным сессиям, и дальше метрики
считаются как операции над множествами. Отсюда автоматически следует устойчивость к повторным
просмотрам, возвратам назад, дублям и событиям, пришедшим не по порядку: порядок и кратность событий
на результат не влияют вообще.

| Показатель | Определение |
| --- | --- |
| Начали воронку | Число сессий, попавших в фильтр |
| Вошли на шаг | Уникальные сессии с `step_viewed` этого шага |
| Ответили на шаге | Уникальные сессии с `step_completed` этого шага |
| Дошли дальше | Сессии, вошедшие на шаг, у которых есть `step_viewed` любого более позднего шага **их собственного варианта** или `result_viewed` |
| Отвал | Вошли − Дошли дальше |
| Конверсия дальше | Дошли дальше / Вошли |
| Доля от старта | Вошли / Начали воронку |
| Дошли до результата | Уникальные сессии с `result_viewed` |
| CTR CTA | Уникальные сессии с `cta_clicked` / Начали воронку |
| Uplift | (метрика варианта − метрика контроля) / метрика контроля; контроль — первый вариант по порядку сортировки. При двух вариантах это привычное «B к A», при большем числе дашборд показывает uplift каждого варианта к контролю, а KPI-карточка — лучший из них |

«Более поздний шаг» определяется по `stepSequence` **того варианта и той версии, к которым привязана
сессия**, а не по общему порядку таблицы. Поэтому вариант B, у которого вопросы идут в другом порядке,
не выглядит «вернувшимся назад».

Фильтры дашборда (и в API, и в UI): версия, вариант, `utm_campaign`, интервал дат. Разрезы: по варианту, по версии,
по кампании и по экрану результата. Отдельный блок «качество данных» показывает, сколько событий
в выборке, сколько пришло не по порядку (инверсии `seq` относительно порядка поступления) и сколько
сессий возвращались назад — эти три метрики уважают фильтры. Счётчики приёма — отброшенные дубли и
отклонённые попытки — глобальные и на дашборде явно подписаны как «за всё время»: у отклонённой
попытки часто нет ни валидной сессии, ни даты, к которым её можно было бы отнести при фильтрации.

## HTTP API

### Публичные

| Метод | Путь | Что делает |
| --- | --- | --- |
| `GET` | `/api/health` | Проверка живости |
| `POST` | `/api/sessions` | Создаёт сессию на активной версии. Принимает `{ variant, utm }` в теле и `?variant=&utm_*=` в query. Возвращает сессию вместе с собранным конфигом варианта |
| `GET` | `/api/sessions/:id` | Полное состояние: конфиг, ответы, текущий шаг, видимый путь, прогресс, выбранный результат. 410, если сессия истекла |
| `POST` | `/api/sessions/:id/answer` | `{ step_id, value }` — валидирует, сохраняет, пересчитывает видимость и следующий шаг |
| `POST` | `/api/sessions/:id/navigate` | `{ step_id }` — переход на видимый шаг (кнопка «Назад») |
| `POST` | `/api/events` | Приём события или пачки |

### Внутренние (`x-admin-token`, если задан `ADMIN_TOKEN`)

| Метод | Путь | Что делает |
| --- | --- | --- |
| `GET` | `/api/admin/versions` | Версии, активная, журнал переключений, список конфигов в репозитории |
| `POST` | `/api/admin/versions` | Публикация: `{ file }` из `configs/` либо `{ config }` инлайном, плюс `notes`, `activate` |
| `POST` | `/api/admin/versions/:version/activate` | Активация или откат |
| `GET` | `/api/admin/versions/:version/config` | Конфиг конкретной версии |
| `GET` | `/api/admin/analytics` | Метрики с фильтрами `version`, `variant`, `utm_campaign`, `from`, `to` |
| `POST` | `/api/admin/seed` | Запуск генератора трафика против собственного API: `{ sessions?, seed? }` |
| `GET` | `/api/admin/events/:eventId` | Отладочное чтение одного события |

Валидация ответа всегда происходит на сервере, даже если клиент уже проверил её тем же кодом
из `packages/shared`. Ответ на невидимый при текущих ответах шаг отклоняется. При смене раннего
ответа, который скрывает часть шагов, ответы на ставшие невидимыми шаги удаляются — иначе сводка
на экране результата показывала бы данные из «мёртвой» ветки.

`navigate` пускает только назад и до первого неотвеченного шага включительно. Без этого ограничения
редактирование `?step=` в адресной строке позволяло бы перепрыгнуть на экран результата, не ответив
ни на один вопрос, — сессия помечалась бы завершённой и раздувала конверсию. Вперёд можно попасть
только через `answer`, то есть через валидацию.

## Генератор тестового трафика

```bash
npm run seed                                        # 120 сессий на http://localhost:3000
npm run seed -- --sessions=300 --seed=7             # больше сессий, другой сценарий
npm run seed -- --url=https://example.com           # против задеплоенного стенда
```

Тот же генератор доступен кнопкой «Сгенерировать 100 тестовых сессий» на дашборде: она дёргает
`POST /api/admin/seed`, который вызывает ту же самую функцию против собственного HTTP API сервера.
Команда и кнопка используют один код — различие только в способе запуска.

Генератор ходит по **реальному HTTP API**, а не пишет в базу напрямую, — то есть заодно проверяет
идемпотентность, валидацию и ветвления. Детерминизм — посессионный и в границах клиента: каждая
сессия получает собственный генератор псевдослучайности, выведенный из `--seed` и номера сессии,
поэтому сценарий сессии — ответы, точка отвала, возвраты, дубли, ретраи пачек, перемешивание
порядка — не зависит от того, в каком порядке восемь конкурентных воркеров получают ответы сети.

Полностью побайтового повтора прогона не бывает **по построению**: вариант эксперимента назначает
сервер хэшем от случайного `session_id`, и генератор сознательно не подменяет серверное назначение
принудительным override — данные с `variant_source = "assigned"` реалистичнее, чем воспроизводимость.
Два прогона с одним сидом дают одинаковый сценарий поведения, но разное распределение сессий по
вариантам. События генератор шлёт строго по контракту из конфига: те имена и те свойства,
что объявлены в `events.allowed`.

Что он воспроизводит:

- разные наборы UTM-меток, включая полное их отсутствие;
- оба варианта эксперимента, включая ~6% сессий с принудительным override;
- разные ветки воронки: remote без вопроса об офисных днях, hybrid и office — с ним;
- все четыре экрана результата;
- отвал на разных шагах с разной вероятностью;
- повторные `step_viewed` и случайные полные дубли событий;
- возвраты назад с последующим повторным проходом;
- отправку событий пачками разного размера;
- повторную отправку той же пачки (~15% пачек) — имитация ретрая после timeout;
- перемешанный порядок событий внутри пачки (~25% пачек).

После прогона печатается сводка: сессии, дошедшие до результата, принятые события, отброшенные дубли,
отклонённые, распределение отвалов по шагам и распределение по экранам результата.

## Деплой

**Живой стенд: https://109-120-178-184.sslip.io**

Админка стенда закрыта токеном (`ADMIN_TOKEN` в systemd-юните): внутренние ручки требуют заголовок
`x-admin-token`, сравнение — через digest и `timingSafeEqual`. Сам токен передаётся вместе со ссылками

rate limit'ом (`RATE_LIMIT_MAX`, по умолчанию 3000 запросов в минуту с IP; локальные запросы вне
лимита, чтобы генератор трафика с самого сервера работал без ограничений).

### Как это развёрнуто

Приложение собирается в один процесс: Fastify отдаёт и API, и статику фронтенда. Перед ним nginx
как reverse proxy и сертификат Let's Encrypt. Docker не используется — на одноядерной машине
нативный запуск экономнее.

| Компонент | Значение |
| --- | --- |
| Сервер | Ubuntu 22.04, 1 vCPU, 2 GB RAM, 30 GB NVMe |
| Node.js | 24.19 (nodesource) |
| Процесс | systemd-юнит `funnel-runtime`, пользователь `funnel`, слушает `127.0.0.1:3000` |
| База | `/var/lib/funnel-runtime/funnel.sqlite`, единственный writable путь для сервиса |
| Прокси | nginx → `127.0.0.1:3000`, редирект с http на https |
| Сертификат | Let's Encrypt на `sslip.io`, автопродление через `certbot.timer` |
| Потребление | ~120 MB RSS, ~10 KB базы на сессию, сборка около 20 секунд |

Файлы для воспроизведения — в [`deploy/`](deploy):

```bash
scp deploy/funnel-runtime.service root@SERVER:/etc/systemd/system/
sed 's/FUNNEL_HOST/ваш.домен/' deploy/nginx.conf > /etc/nginx/sites-available/funnel-runtime
```

Обновление кода на стенде:

```bash
DEPLOY_HOST=root@SERVER DEPLOY_KEY=~/.ssh/ваш_ключ ./deploy/deploy.sh
```

Скрипт синхронизирует исходники, ставит зависимости, собирает и перезапускает сервис,
после чего проверяет `/api/health`.

### Альтернативы

`docker compose up --build` поднимает то же самое в контейнере с volume под базу.

Единственное требование к площадке — постоянный диск для файла SQLite: `DATA_DIR` должен указывать
на примонтированный volume. Платформы с эфемерной файловой системой (Render free, Vercel, Netlify,
Cloudflare Workers) не подойдут без замены хранилища.

| `packages/shared` | zod-схемы конфига, интерпретатор условий, резолв варианта, видимость шагов, прогресс, выбор результата, валидация |
| Бэкенд | Миграции, хранилище версий, сессии с закреплением версии и TTL, назначение варианта, идемпотентный приём событий |
| Аналитика | Агрегация по уникальным сессиям, разрезы по варианту / версии / кампании / результату, блок качества данных |
| Фронтенд | Рантайм воронки с синхронизацией шага через History API, админка версий, дашборд |
| Генератор и тесты | Генератор синтетического трафика, 33 автотеста |
| Деплой | Публичный стенд на VPS: systemd, nginx, Let's Encrypt |

**Вторая итерация** — `configs/funnel-v2.json`: новая условная ветка `meeting_load` (видна, когда
решения обсуждаются на встречах), у варианта B удалён экран `tool_count`, добавлено событие
`recommendation_expanded` и новое правило выбора результата. Новое событие не только принимается
сервером — его реально отправляют и фронтенд (при раскрытии списка рекомендаций), и генератор
трафика, но только если сессия живёт на версии, где оно объявлено. Изменения потребовали ровно
одной публикации через админку: ни схема базы, ни код не менялись.

Полный цикл прогнан на стенде и виден в журнале переключений: публикация второй версии → трафик →
откат на первую → трафик → возврат на вторую. Сессии, начатые до публикации, дошли до результата
на своей версии без ошибок, аналитика по обеим версиям сохранилась целиком.

## Ограничения и допущения

**Осознанные упрощения**

- Аналитика считает агрегаты в памяти процесса поверх `DISTINCT`-выборки из SQLite. Это даёт полностью
  корректный счёт по множествам сессий и читаемый код, но при сотнях тысяч сессий понадобятся
  предрасчитанные роллапы или оконные функции в SQL.
- A/B-модуль не считает статистическую значимость: показываются абсолютные значения и uplift.
  Решение о победителе принимает человек.
- Авторизация админки — один общий токен через `ADMIN_TOKEN` (на стенде включён). Ролей и учёток
  нет: по ТЗ достаточно простой внутренней страницы.
- Сессия опознаётся по идентификатору в `localStorage`. Очистка хранилища или другой браузер — новая
  сессия. Cookie не используются, чтобы не тянуть согласие на трекинг.
- Один процесс и один файл SQLite (WAL). Горизонтальное масштабирование потребует другого хранилища.

**Допущения по конфигам**

- В задании упомянуты **два** локальных конфига, прислан был один (`funnel-v1.json`). Второй
  (`funnel-v2.json`) написан мной в том же формате, чтобы показать версионирование, сравнение версий
  на дашборде и сценарий второй итерации. Когда придёт настоящий, он подставляется без изменений кода:
  достаточно положить файл в `configs/` и опубликовать через админку.
- `stepOverrides` трактуются как патч: `content`, `input` и `validation` сливаются по ключам,
  остальные поля заменяются целиком. Это предсказуемее полного глубокого слияния.
- Язык условий реализован шире, чем использует присланный конфиг (добавлены `contains*`, сравнения
  чисел, `between`, `none`). Лишние операторы ничего не ломают, но снимают риск, что следующая
  итерация упрётся в выразительность.
- `node:sqlite` в Node.js помечен как экспериментальный API. Он выбран ради нулевых нативных
  зависимостей: `npm install` не требует компилятора. Замена на `better-sqlite3` — это правки только
  в `apps/api/src/db/database.ts`.
