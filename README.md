# Funnel Runtime

Мини-платформа для запуска, версионирования и анализа многошаговых веб-воронок.

Фронтенд не содержит ни одного захардкоженного экрана: вся воронка — шаги, тексты, валидация,
условные переходы, экран результата — приходит с бэкенда JSON-конфигом. Версии конфига публикуются
и откатываются без передеплоя, сессия навсегда закрепляется за той версией, на которой началась,
а события пишутся в собственный идемпотентный endpoint и агрегируются по уникальным сессиям.

Всё содержимое воронок вымышленное. Внешних сервисов нет: хранилище — SQLite внутри проекта.

## Быстрый старт

Требуется **Node.js 24+** (используется встроенный модуль `node:sqlite`, без нативных зависимостей).

```bash
npm install
npm run dev
```

- воронка — http://localhost:5173
- управление версиями — http://localhost:5173/admin/versions
- дашборд — http://localhost:5173/admin/analytics

Vite проксирует `/api` на бэкенд (http://localhost:3000). При первом запуске сервер сам публикует
`configs/funnel.v1.json` как активную версию и создаёт `data/funnel.sqlite`.

Наполнить базу синтетическим трафиком (сервер должен быть запущен):

```bash
npm run seed
```

Сборка и запуск одним процессом (API отдаёт и статику фронтенда):

```bash
npm run build
npm start
```

Полезное:

```bash
npm test          # автотесты
npm run typecheck # tsc по всем пакетам
npm run reset     # удалить базу и начать с чистого листа
```

Переменные окружения — в [.env.example](.env.example). Если задать `ADMIN_TOKEN`, внутренние страницы
начнут требовать заголовок `x-admin-token` (поле для токена есть в самой админке).

## Что где лежит

```
configs/                    JSON-конфиги воронок (публикуются через админку)
packages/shared/            Общий код фронта и бэка
  src/funnel-config.ts        zod-схема конфига + валидация целостности
  src/conditions.ts           язык условий и его интерпретатор
  src/resolve.ts              сборка варианта, вычисление пути и прогресса, валидация ответов
  src/events.ts               схема входящего события
  src/api-types.ts            контракты ответов API
apps/api/                   Fastify + SQLite
  src/db/                     подключение и миграции
  src/domain/                 версии, сессии, приём событий, аналитика, назначение варианта
  src/routes/                 публичные и админские ручки
  src/scripts/                генератор трафика
  tests/                      vitest
apps/web/                   React + Vite
  src/funnel/                 рантайм воронки
  src/admin/                  версии и дашборд
  src/lib/tracker.ts          очередь событий с батчингом и ретраями
```

Ключевое решение: `packages/shared` — единственный источник правды о структуре воронки. Бэкенд и
фронтенд считают путь, прогресс и валидность ответа **одним и тем же кодом**, поэтому клиент не может
разойтись с сервером в понимании ветвлений.

## Конфиг воронки

Один конфиг описывает воронку целиком: общий пул шагов и два варианта эксперимента поверх него.

```jsonc
{
  "schemaVersion": 1,
  "funnelId": "renovation-quote",
  "name": "Расчёт ремонта под ключ",
  "experiment": { "key": "budget_position_v1", "hypothesis": "…", "primaryMetric": "cta_ctr" },
  "extraEvents": ["hint_opened"],
  "steps": [ /* пул всех экранов */ ],
  "result": { /* экран результата по умолчанию */ },
  "variants": [
    { "key": "A", "label": "…", "weight": 50, "stepOrder": ["intro", "…"], "overrides": {}, "result": {} },
    { "key": "B", "label": "…", "weight": 50, "stepOrder": ["…"], "overrides": { "budget": { "title": "…" } },
      "result": { "cta": { "label": "…" } } }
  ]
}
```

**Типы шагов:** `info`, `single_select`, `multi_select`, `number`.

**Вариант** задаётся тремя вещами:

- `stepOrder` — какие экраны существуют в этом варианте и в каком порядке идут по умолчанию;
- `overrides` — поверхностный патч конкретных шагов (тексты, опции, `next`);
- `result` — патч экрана результата.

Чтобы убрать экран у варианта B (требование второй итерации), достаточно не упомянуть его в `stepOrder`
варианта B. Переходы, ведущие на отсутствующий экран, при сборке варианта отбрасываются, и шаг просто
отдаёт следующий доступный.

**Условные переходы.** У шага есть необязательный список `next`; выигрывает первое правило, чьё условие
истинно, правило без `when` — безусловный fallback. Если правил нет, берётся следующий экран из `stepOrder`.

```json
"next": [
  { "when": { "op": "includes", "step": "works", "value": "design" }, "goto": "design_style" },
  { "goto": "property_state" }
]
```

Поддерживаемые операторы: `always`, `eq`, `neq`, `in`, `includes`, `includesAny`, `countGte`,
`gt`, `gte`, `lt`, `lte`, `answered`, а также композиты `and`, `or`, `not`.

**Прогресс** считается не по общему числу экранов, а по *проекции пути*: из текущих ответов
вычисляется список шагов, которые пользователь реально увидит (`computePath`). Ответ на шаг с
ветвлением мгновенно меняет знаменатель прогресса.

**Целостность конфига** проверяется zod-схемой при публикации: уникальность id шагов, существование
целей переходов, отсутствие дублей в `stepOrder`, минимум 6 экранов на вариант, ровно один A и один B.
Невалидный конфиг не публикуется — 400 с перечнем проблем.

Визуальный редактор конфигов не делался (по ТЗ не требуется): публикация идёт файлом из репозитория
или вставкой JSON в поле админки.

### Что лежит в `configs/`

| Файл | Что это |
| --- | --- |
| `funnel.v1.json` | Базовая воронка: 9 экранов, два ветвления (тип объекта, размер бюджета) |
| `funnel.v2.json` | Расширенная анкета: +2 экрана (канал связи, гарантии), переработанные тексты |
| `funnel.v3.json` | **Вторая итерация:** новая условная ветка `design_style`, у варианта B удалён экран `property_state`, добавлено событие `hint_opened` |

Имя файла не равно номеру версии: номер выдаёт база при публикации (первая опубликованная — 1, вторая — 2
и так далее), поэтому один и тот же файл можно опубликовать повторно и получить новую версию.

## Версионирование и откат

- `funnel_versions` хранит все опубликованные конфиги, `funnel_state.active_version` — текущий активный.
- **Публикация** не требует передеплоя: конфиг попадает в базу и активируется одним запросом.
- **Сессия закрепляется за версией** в момент создания (`sessions.funnel_version`) и больше её не меняет.
  Публикация новой версии не влияет ни на одну живую сессию: она дочитает свои экраны на старом конфиге.
- **Новые сессии** стартуют только на активной версии.
- **Откат** — это активация более раннего номера. Отдельной сущности «rollback» нет: событие пишется
  в журнал `version_activations` с действием `rollback`, если новый номер меньше текущего.
- Аналитика при откате не теряется: события хранят номер версии, дашборд умеет сравнивать версии.

Схема базы при этом не меняется. Новый тип события из второй итерации (`hint_opened`) не требует
миграции: `events.type` — обычная строка, а список допустимых типов для конкретной версии берётся из
её же конфига (`extraEvents`). Событие, не объявленное в версии сессии, отклоняется как
`unknown_event_type` — это защита от мусора, а не ограничение схемы.

Демонстрация второй итерации целиком:

```bash
npm start                                    # активна версия 1
npm run seed                                 # трафик на версии 1
# в админке публикуем configs/funnel.v3.json → становится версией 2
npm run seed -- --seed=7 --sessions=60       # трафик на версии 2, старые сессии живы
# в админке жмём «Откатить сюда» на версии 1
```

## A/B-эксперимент: гипотеза и метрика

**Гипотеза.** Вопрос о бюджете в середине воронки — самый «дорогой» для пользователя: на нём он впервые
раскрывает деньги, ещё не получив ничего взамен. Если перенести бюджет в конец анкеты (вариант B),
отвал в середине снизится, и больше сессий дойдёт до результата и нажмёт основной CTA.

Вариант B меняет три вещи одновременно: порядок шагов (бюджет последним), тексты вводного экрана
и экрана бюджета, а также экран результата с более конкретным CTA («Получить смету за 2 часа»
вместо «Получить смету на почту»).

**Основная метрика:** `cta_ctr` — доля уникальных сессий, в которых был `cta_clicked`, от всех сессий
варианта. Дашборд показывает её и uplift B к A.

**Вспомогательные метрики:** конверсия в результат (`result_viewed` / сессии) и пошаговый отвал —
чтобы отличить «CTR вырос, потому что дошло больше людей» от «CTR вырос при том же трафике».

**Назначение варианта** делает бэкенд в момент создания сессии: `sha256(salt + experiment_key + session_id)`
раскладывается по весам вариантов, результат сразу пишется в `sessions.variant`. Поэтому вариант стабилен
по построению — он не пересчитывается ни при refresh, ни при переоткрытии страницы. Для ручной проверки
есть override: `?variant=B` при первом заходе; такая сессия помечается `variant_source = "override"`
и её видно в данных.

Резолв варианта выполняется **на сервере**: клиент получает уже собранный конфиг своего варианта и
физически не видит альтернативный.

## Модель данных

SQLite, миграции применяются при старте (`schema_migrations` + список в `apps/api/src/db/migrations.ts`).

| Таблица | Назначение |
| --- | --- |
| `funnel_versions` | `version` (PK), `funnel_id`, `name`, `config_json`, `checksum`, `source`, `notes`, `created_at` |
| `funnel_state` | Одна строка: `active_version` |
| `version_activations` | Журнал: `version`, `action` (`publish` / `activate` / `rollback`), `actor`, `note`, `created_at` |
| `sessions` | `id` (uuid), `funnel_version`, `variant`, `variant_source`, `current_step_id`, пять `utm_*`, `created_at`, `last_seen_at`, `completed_at` |
| `session_answers` | `(session_id, step_id)` → `value_json`. **Сырые ответы живут только здесь** |
| `events` | `event_id` (PK), `session_id`, `type`, `funnel_version`, `variant`, `step_id`, `seq`, `client_ts`, `server_ts`, пять `utm_*`, `props_json` |
| `ingest_stats` | Счётчики принятых / отброшенных как дубли / отклонённых событий |

Разделение `session_answers` и `events` — сознательное: ответы пользователя нужны рантайму воронки
(чтобы посчитать ветвление и показать сводку на результате), но в аналитику они не попадают.
В событии `answer_submitted` остаются только метаданные ответа.

## Event schema

Тело запроса — либо одно событие, либо пачка `{ "events": [...] }`.

Клиент присылает:

| Поле | Тип | Обязательно |
| --- | --- | --- |
| `event_id` | string, 8..64 символа, уникальный | да |
| `session_id` | string | да |
| `type` | snake_case | да |
| `client_ts` | ISO 8601 со смещением | да |
| `seq` | int, порядковый номер внутри сессии | нет |
| `step_id` | string | для шаговых событий — да |
| `props` | объект скаляров | нет |

Сервер добавляет: `server_ts`, `funnel_version`, `variant`, `utm_*`. Эти поля **выводятся из сессии**,
а не берутся с клиента — иначе версию и вариант можно было бы подменить и испортить аналитику.

**Типы событий:** `session_started`, `step_viewed`, `answer_submitted`, `step_completed`,
`back_clicked`, `result_viewed`, `cta_clicked`. Версия конфига может добавлять свои через `extraEvents`
(во второй итерации это `hint_opened`).

Для `step_viewed`, `answer_submitted`, `step_completed`, `back_clicked` поле `step_id` обязательно и
проверяется на принадлежность варианту версии этой сессии.

### Инварианты приёма

| Требование | Как обеспечено |
| --- | --- |
| Повторный `event_id` не создаёт дубль | `event_id` — первичный ключ, вставка через `INSERT OR IGNORE`; дубли внутри пачки схлопываются до вставки |
| Пачки | `POST /api/events` принимает до 500 событий за раз, вставка в одной транзакции |
| Повторный запрос после timeout безопасен | Приём полностью идемпотентен: повторная отправка той же пачки даёт `accepted: 0, duplicates: N` |
| Одно плохое событие не ломает пачку | Каждое событие валидируется отдельно; плохие возвращаются в `rejected` с причиной, остальные принимаются |
| Сырые ответы не утекают в аналитику | Для `answer_submitted` из `props` пропускаются только `value_type`, `option_count`, `value_bucket`, `attempt`, `is_valid`; всё остальное отбрасывается на входе |

Ответ:

```json
{ "received": 6, "accepted": 4, "duplicates": 1, "rejected": [{ "index": 2, "event_id": "…", "reason": "unknown_session" }] }
```

Причины отклонения: `validation_failed`, `unknown_session`, `unknown_event_type`, `missing_step_id`, `unknown_step`.

### Клиентская доставка

`apps/web/src/lib/tracker.ts` держит очередь в памяти и в `localStorage`, отправляет пачками
(по 25 событий или раз в 2 секунды), при неудаче оставляет пачку в очереди и повторяет позже,
а на `pagehide` досылает хвост через `sendBeacon`. Поскольку `event_id` генерируется в момент
постановки в очередь, любые повторы схлопываются на сервере.

## Правила агрегации

Главный принцип: **все показатели считаются по уникальным сессиям, а не по количеству событий.**

Из базы забираются `DISTINCT (session_id, type, step_id)` по отфильтрованным сессиям, и дальше метрики
считаются как операции над множествами. Отсюда автоматически следует устойчивость к повторным
просмотрам, возвратам назад, дублям и событиям, пришедшим не по порядку: порядок и кратность событий
на результат не влияют вообще.

| Показатель | Определение |
| --- | --- |
| Начали воронку | Число сессий, попавших в фильтр |
| Вошли на шаг | Уникальные сессии с `step_viewed` этого шага |
| Ответили на шаге | Уникальные сессии с `step_completed` этого шага |
| Дошли дальше | Сессии, вошедшие на шаг, у которых есть `step_viewed` любого более позднего шага **их собственного варианта** или `result_viewed` |
| Отвал | Вошли − Дошли дальше |
| Конверсия дальше | Дошли дальше / Вошли |
| Доля от старта | Вошли / Начали воронку |
| Дошли до результата | Уникальные сессии с `result_viewed` |
| CTR CTA | Уникальные сессии с `cta_clicked` / Начали воронку |
| Uplift | (метрика B − метрика A) / метрика A |

«Более поздний шаг» определяется по порядку шагов **того варианта и той версии, к которым привязана
сессия**, а не по общему порядку таблицы. Поэтому вариант B, у которого бюджет стоит последним, не
считается «вернувшимся назад» из-за другого порядка экранов.

Фильтры дашборда: версия, вариант, `utm_campaign`, интервал дат. Разрезы: по варианту, по версии,
по кампании. Отдельный блок «качество данных» показывает, сколько событий было отброшено как дубли,
сколько отклонено и сколько пришло не по порядку (инверсии `seq` относительно порядка поступления).

## HTTP API

### Публичные

| Метод | Путь | Что делает |
| --- | --- | --- |
| `GET` | `/api/health` | Проверка живости |
| `POST` | `/api/sessions` | Создаёт сессию на активной версии. Принимает `{ variant, utm }` в теле и `?variant=&utm_*=` в query. Возвращает сессию вместе с собранным конфигом варианта |
| `GET` | `/api/sessions/:id` | Полное состояние сессии: конфиг, ответы, текущий шаг, путь, прогресс |
| `POST` | `/api/sessions/:id/answer` | `{ step_id, value }` — валидирует, сохраняет, вычисляет следующий шаг |
| `POST` | `/api/sessions/:id/navigate` | `{ step_id }` — переход на шаг текущего пути (кнопка «Назад») |
| `POST` | `/api/events` | Приём события или пачки |
| `GET` | `/api/events/:eventId` | Отладочное чтение одного события |

### Внутренние (`x-admin-token`, если задан `ADMIN_TOKEN`)

| Метод | Путь | Что делает |
| --- | --- | --- |
| `GET` | `/api/admin/versions` | Версии, активная, журнал переключений, список конфигов в репозитории |
| `POST` | `/api/admin/versions` | Публикация: `{ file }` из `configs/` либо `{ config }` инлайном, плюс `notes`, `activate` |
| `POST` | `/api/admin/versions/:version/activate` | Активация или откат |
| `GET` | `/api/admin/versions/:version/config` | Конфиг конкретной версии |
| `GET` | `/api/admin/analytics` | Метрики с фильтрами `version`, `variant`, `utm_campaign`, `from`, `to` |

Валидация ответа на шаг всегда происходит на сервере, даже если клиент уже проверил её тем же кодом
из `packages/shared`. Ответ на недостижимый при текущих ответах шаг отклоняется.

## Генератор тестового трафика

```bash
npm run seed                                        # 120 сессий на http://localhost:3000
npm run seed -- --sessions=300 --seed=7             # больше сессий, другой сценарий
npm run seed -- --url=https://example.com           # против задеплоенного стенда
```

Генератор ходит по **реальному HTTP API**, а не пишет в базу напрямую, — то есть заодно проверяет
идемпотентность, валидацию и ветвления. Псевдослучайность детерминирована сидом.

Что он воспроизводит:

- разные наборы UTM-меток, включая полное их отсутствие;
- оба варианта эксперимента, включая ~6% сессий с принудительным override;
- разные ветки воронки (квартира / дом / коммерция, дорогой и дешёвый бюджет, дизайн-проект);
- отвал на разных шагах с разной вероятностью;
- повторные `step_viewed` и случайные полные дубли событий;
- возвраты назад с последующим повторным проходом;
- отправку событий пачками разного размера;
- повторную отправку той же пачки (~15% пачек) — имитация ретрая после timeout;
- перемешанный порядок событий внутри пачки (~25% пачек).

После прогона генератор печатает сводку: сколько сессий, сколько дошло до результата, сколько событий
принято, сколько отброшено как дубли, сколько отклонено, и распределение отвалов по шагам.

## Деплой

Публичный URL: _уточняется_.

Приложение собирается в один процесс: Fastify отдаёт и API, и статику фронтенда.

```bash
docker compose up --build     # http://localhost:3000, база в volume funnel-data
```

или без Docker:

```bash
npm ci && npm run build && npm start
```

Единственное требование к площадке — постоянный диск для файла SQLite: `DATA_DIR` должен указывать
на примонтированный volume. Платформы, где файловая система эфемерна между запросами, не подойдут
без замены хранилища.

## Ограничения и допущения

**Осознанные упрощения**

- Аналитика считает агрегаты в памяти процесса поверх `DISTINCT`-выборки из SQLite. Это даёт полностью
  корректный счёт по множествам сессий и читаемый код, но при сотнях тысяч сессий понадобятся
  предрасчитанные роллапы или оконные функции в SQL.
- A/B-модуль не считает статистическую значимость: показываются абсолютные значения и uplift.
  Решение о победителе принимает человек.
- Авторизация админки — один общий токен через `ADMIN_TOKEN`. Ролей и учёток нет: по ТЗ достаточно
  простой внутренней страницы. Если переменная не задана, админка открыта — удобно для ревью,
  но на публичном стенде токен стоит задать.
- Сессия опознаётся по идентификатору в `localStorage`. Очистка хранилища или другой браузер — новая
  сессия. Cookie не используются, чтобы не тянуть согласие на трекинг.
- Один процесс и один файл SQLite (WAL). Горизонтальное масштабирование потребует другого хранилища.

**Допущения по содержанию**

- Оригинальные конфиги к заданию не прилагались, поэтому воронка и её содержимое написаны с нуля:
  вымышленная компания, вымышленные работы и цены. Структура покрывает все требования ТЗ — четыре типа
  экранов, два ветвления, минимум шесть экранов на вариант.
- `overrides` в варианте — поверхностный патч: указанное поле заменяется целиком (например, `next`
  переопределяется списком, а не сливается поэлементно). Это предсказуемее глубокого слияния.
- При изменении раннего ответа, меняющего ветку, ответы на ставшие недостижимыми шаги удаляются.
  Иначе сводка на экране результата показывала бы данные из «мёртвой» ветки.
- `node:sqlite` в Node.js помечен как экспериментальный API. Он выбран ради нулевых нативных
  зависимостей: `npm install` не требует компилятора. При необходимости замена на `better-sqlite3` —
  это правки только в `apps/api/src/db/database.ts`.
